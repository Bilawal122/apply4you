## The correction: P0-01 was a false alarm, and I can prove it

The audit reported the live worker as dead at 00:48:45 UTC — `worker alive:
false, lastSeen: null` — and concluded **"the core queue-to-review path is
currently unavailable."**

That conclusion is wrong. The worker was alive and working hard at the time.
Measured against the production database at 00:56, eight minutes after the
audit's reading:

| | |
|---|---|
| Last AI call | **37 seconds ago** |
| AI calls in the preceding 10 minutes | **900** |
| Embedding backlog | 9,636 → **7,751**, draining ~90/min |
| Drafts stuck unfilled | **0** |

**Both observations are correct.** The explanation is a version mismatch: the
worker running in production was deployed from `master` at `e2d570e`, *before*
the heartbeat existed. The heartbeat is code that merged at `00f90f9`. A worker
that predates it processes the queue perfectly while publishing no heartbeat —
so the health endpoint reports precisely what a dead worker reports.

The audit itself flagged the discrepancy ("investigate the deployment/runtime
mismatch") and was right to trust the live endpoint over my documentation. The
missing piece was that "no heartbeat" had two causes and the endpoint could
only name one.

**The real defect was the diagnostic, so that is what I fixed** — see P1-06
below. The residual operational item is genuine and stands: the Railway
redeploy after the merge did not take effect, so production is still running
pre-merge worker code.

## The finding underneath it: the website's jobs reach no consumer

*Added 01:50 UTC while trying to perform that redeploy; **conclusion revised
02:20 UTC**, see "Which of the two it is" below. The first version of this
section named the cause with more confidence than the evidence carries.*

The stale-build theory above explains the missing heartbeat. It does **not**
explain the queue counters, and once I looked at those a second fault showed.

Measured twice, ten minutes apart, against the live endpoint and the live
database at the same moments:

| | 01:38:29 UTC | 01:48:04 UTC |
|---|---|---|
| `embedding` queue as Vercel sees it | `waiting 0, active 0` | `waiting 0, active 0` |
| `embed` AI calls in the surrounding 30 min | — | **2,700** (≈90/min, last one seconds before the read) |
| Jobs still missing an embedding | — | **4,789** |
| `resolve` waiting / oldest | 22 / 5.83 d | 22 / 5.83 d |
| `submit-workable` waiting / oldest | 1 / 5.83 d | 1 / 5.83 d |
| `profile-embedding` waiting / oldest | 4 / 4.05 d | 4 / 4.05 d |

Those two columns cannot both describe one Redis.

`startEmbeddingWorker` consumes `QUEUES.embedding` through BullMQ under
`limiter: { max: 90, duration: 60_000 }` and `concurrency: 4`. The observed
rate is ~90/min — the limiter's exact cap — so that worker is saturated, and
with 4,789 jobs still unembedded its queue must hold thousands waiting and up
to four active at essentially every instant. Vercel reads that queue by the
same name and sees it empty and idle, twice.

The counters Vercel *does* return are live, not cached: `x-vercel-cache: MISS`,
`checkedAt` advances, and `oldestWaitingMs` grew by 574,944 ms between the two
reads — 9.58 minutes, matching the 9.58 minutes of wall clock. Redis answered
`PONG` in ~330 ms both times. So Vercel is talking to a real, healthy Redis.
Just not the worker's one.

Both sides build the same keys, so nothing else can account for it:

- `apps/web/lib/queue.ts` and `apps/worker/src/queues.ts` both take their names
  from `QUEUES` in `@apply4you/shared`.
- Neither passes BullMQ a `prefix`.
- Both read the instance from `process.env.REDIS_URL`.

One variable is left in the configuration: the value of `REDIS_URL` could
differ between Railway and Vercel. That was my first conclusion, and I stated
it as settled. It is not — see below.

### What it costs, in production, right now

Everything the website enqueues goes to a queue with no consumer:

- `enqueueResolve` — a user clicking apply. **22 waiting, 5.8 days.** There are
  exactly 22 applications sitting in `draft`.
- `enqueueSubmit` — a user approving an application. **1 waiting, 5.8 days.**
  That is a job somebody approved and no employer ever received.
- `enqueueProfileEmbedding` — a user saving their profile. **4 waiting, 4 days.**
  Until it runs, `match_jobs` cannot match that user at all.

It also means the earlier "the worker is alive, so P0-01 is a false alarm"
finding was right about the worker and wrong about the system. The worker is
alive. The path from the website to it is not carrying anything.

### Settled, 2026-09-02 00:15 UTC: it is A

Railway access finally arrived and the question closed in three reads. Keeping
the reasoning below intact, because being wrong twice in one night about the
same fault is the useful part of the record.

**The worker is running `02455e7` — the commit that *added* the heartbeat.**
Deployed 2026-09-01 01:08:08 UTC, status SUCCESS. Its deploy log is a clean
heartbeat every sixty seconds, still ticking while I read it:

```
[worker] heartbeat 2026-09-02T00:09:15.609Z
[worker] heartbeat 2026-09-02T00:10:15.609Z
[worker] heartbeat 2026-09-02T00:11:15.609Z
```

Vercel, at the same moment, reports `worker.alive: false, lastSeen: null,
version: null`. A worker writing a heartbeat once a minute, and a web app
reading `null` from the key it writes to, cannot be one Redis. **Hypothesis A,
confirmed.** No inference left in it.

Three corrections fall out, all of them mine:

1. **The stale-build story was wrong.** I said the deployed worker predated the
   heartbeat. It doesn't — it *is* the heartbeat commit, and has been since
   01:08. There is no worker-affecting commit after `02455e7`
   (`git log 02455e7..HEAD -- apps/worker packages/*` is empty), so it already
   carries the per-worker connections and the five-minute reconcilers too.
2. **The redeploy was never going to fix anything.** It would have rebuilt the
   identical worker code. Every push after `02455e7` shows `SKIPPED` in
   Railway because the watch paths correctly saw only `apps/web` and docs.
   Hours of trying to get that redeploy done were hours spent on a no-op.
3. **My "22 drafts = 22 resolve jobs" counter-argument had it backwards.**
   I read the match as proof the two sides shared a Redis. It is the opposite:
   the web app enqueues a `resolve` job on every apply click, and those drafts
   are unfilled *because* their jobs are stranded. The counts match because
   they are two views of the same 22 abandoned clicks.

Everything below is the reasoning as it stood before that access, kept for the
record.

### Which of the two it was

There were two explanations, and the evidence available at the time did not
separate them.

**A — different Redis instances.** `REDIS_URL` on Railway names a different
instance from Vercel's. Everything the website enqueues lands where no worker
is attached; the worker only ever does the work it enqueues for itself.

**B — one Redis, and `resolve` is starved.** The deployed build predates the
per-worker-connection fix. Its docblock in `apps/worker/src/queues.ts` records
this failure *from production*, in these words:

> Observed live: the embedding queue (2.5k backlog) ran flat out while
> `resolve` sat at active=0 with 10 jobs waiting and a worker attached.

That is the present symptom almost exactly, at 22 jobs instead of 10. BullMQ
workers block on Redis and ioredis serialises commands per connection, so on
the old shared connection a permanently-backlogged embedding queue starves
every other worker behind it — and with 4,789 jobs still unembedded, that
backlog is permanent.

What favours **B**, and what I under-weighted when I first wrote this section:
the worker's boot reconcilers enqueue `resolve` jobs for stranded drafts, and
there are **exactly 22 stranded drafts and exactly 22 waiting `resolve` jobs**.
If the two sides were on different instances, Vercel could not be looking at
the jobs the worker itself queued. Under **B** the count matches because it is
the same queue.

What favours **A**: `embedding` reads `waiting 0, active 0` on all three
samples while the worker is provably embedding at its limiter's cap. Under
**B** that queue should show up to four active essentially always.

Both readings cannot be right, and I cannot settle it from here — it needs
Railway's `REDIS_URL` or the worker's own logs, neither of which this session
can reach.

### The fix

One change, and it is not a deploy.

1. **Point Vercel at the Railway Redis.** The Railway `Redis` service already
   publishes a public endpoint for exactly this — TCP proxy
   `sakura.proxy.rlwy.net:14056` → 6379, ACTIVE — and exposes it as
   `REDIS_PUBLIC_URL`. Copy that value into the Vercel **production**
   `REDIS_URL` and redeploy the web app. The worker keeps its internal
   hostname: private networking is faster and its egress is free.

   Direction matters. Vercel's functions are off-network, so they can only
   reach Redis over the proxy; the worker is in-network and should not be
   pushed out onto it.

2. **The 22 stranded jobs are not lost by switching.** They are queue entries
   pointing at rows that still exist in Postgres, and the worker's
   `reenqueueStrandedDrafts` sweep rebuilds them on the shared instance within
   five minutes of the change.

3. **Then confirm** on `/api/health/queue`: `"queue":"ok"`, `worker.alive:
   true`, `worker.version` = `02455e7`. If it stays red after that, the
   remaining suspects are proxy reachability and credentials, not the code.

4. **Re-check the `submit-workable` job before it drains.** It is an approved
   application that has been waiting 5.8 days; per DECISIONS.md D3, a
   submission that may already have been attempted is verified against the ATS
   by hand, never auto-retried.

The health endpoint has been telling the exact truth about the queues the
website writes to for days. It simply had no way to say *which* Redis it meant.

## Fixed in this branch

### P1-01 · Production sitemap and robots emitted `localhost` ✅

The audit's most concrete new finding, and a real bug of mine. Live
`/robots.txt` and `/sitemap.xml` returned HTTP 200 — every status check passed
— while the *bodies* told crawlers to visit `http://localhost:3000`. `APP_URL`
was never set in the Vercel production environment, and the
`?? "http://localhost:3000"` fallback I wrote for `next dev` quietly became the
published answer.

Setting `APP_URL` alone would fix today's symptom and leave the trap armed, so:

- [x] **`apps/web/lib/origin.ts`** — one canonical resolver: `APP_URL`, then
      Vercel's own `VERCEL_PROJECT_PRODUCTION_URL` / `VERCEL_URL` (always
      present on Vercel, supplied without a scheme), and localhost **only**
      when nothing indicates a deployment. A deployed build can no longer
      reach the localhost branch even if `APP_URL` is forgotten again.
      Deliberately not derived from the `Host` header: this feeds crawler
      output, and `Host` is attacker-controlled.
- [x] **11 unit tests** pinning each branch, including the exact production
      case (Vercel env present, `APP_URL` absent) and every loopback form.
- [x] **`scripts/check-seo-origin.mjs`** — the CI assertion the audit asked
      for. Next prerenders these routes at build time, so it reads the
      generated bodies directly. **Verified against the real bug**: built
      without an origin it fails and prints the offending body; built with
      Vercel's env it reports `https://apply4you.vercel.app/sitemap.xml`.
- [x] **CI wiring** — the build step now supplies a production-like origin and
      the guard runs after it, so the tested path is the real one.
- [x] **`turbo.json`** — `APP_URL`, `VERCEL_URL` and
      `VERCEL_PROJECT_PRODUCTION_URL` declared as build inputs. Without this
      turbo would replay a cached build whose SEO body names a different host,
      and the guard would be checking a stale artifact.

Still yours: **set `APP_URL` in Vercel Production** to the canonical origin.
The code now degrades to the correct Vercel hostname instead of localhost, but
only `APP_URL` can name a custom domain, and the audit is right that the
`apply4you-web-one` → `apply4you.vercel.app` alias should be settled
deliberately.

### P1-06 (new) · A stale worker build was indistinguishable from a dead one ✅

This is the defect behind the false P0 above, and it will recur on every
deploy that lags the web app.

- [x] The worker now publishes its **commit SHA** in the heartbeat.
- [x] `queueHealth()` reports **`consumerObserved`** — BullMQ marks a job
      `active` only once a worker has claimed it, so an active job is positive
      proof of a consumer, entirely independent of the heartbeat.
- [x] `/api/health/queue` now distinguishes three red states instead of one:

      | state | meaning | action |
      |---|---|---|
      | `unreachable` | Redis did not answer | fix Redis |
      | `no-consumer` | Redis fine, no heartbeat, nothing active | start the worker |
      | `stale-worker-build` | Redis fine, jobs **active**, no heartbeat | redeploy the worker from current master |

      All three remain **503**. An endpoint that goes green on an inference is
      the failure this route exists to prevent; the point is to name the cause,
      not to soften the verdict.
- [x] The watchdog workflow's alert text now explains which state means what.

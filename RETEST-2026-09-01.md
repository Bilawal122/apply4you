## The correction: P0-01 was a false alarm, and I can prove it

The audit reported the live worker as dead at 00:48:45 UTC — `worker alive:
false, lastSeen: null` — and concluded **"the core queue-to-review path is
currently unavailable."**

That conclusion is wrong. The worker was alive and working hard at the time.
Measured against the production database at 00:56, eight minutes after the
audit's reading:

| | |
|---|---|
| Last AI call | **37 seconds ago** |
| AI calls in the preceding 10 minutes | **900** |
| Embedding backlog | 9,636 → **7,751**, draining ~90/min |
| Drafts stuck unfilled | **0** |

**Both observations are correct.** The explanation is a version mismatch: the
worker running in production was deployed from `master` at `e2d570e`, *before*
the heartbeat existed. The heartbeat is code that merged at `00f90f9`. A worker
that predates it processes the queue perfectly while publishing no heartbeat —
so the health endpoint reports precisely what a dead worker reports.

The audit itself flagged the discrepancy ("investigate the deployment/runtime
mismatch") and was right to trust the live endpoint over my documentation. The
missing piece was that "no heartbeat" had two causes and the endpoint could
only name one.

**The real defect was the diagnostic, so that is what I fixed** — see P1-06
below. The residual operational item is genuine and stands: the Railway
redeploy after the merge did not take effect, so production is still running
pre-merge worker code.

## Fixed in this branch

### P1-01 · Production sitemap and robots emitted `localhost` ✅

The audit's most concrete new finding, and a real bug of mine. Live
`/robots.txt` and `/sitemap.xml` returned HTTP 200 — every status check passed
— while the *bodies* told crawlers to visit `http://localhost:3000`. `APP_URL`
was never set in the Vercel production environment, and the
`?? "http://localhost:3000"` fallback I wrote for `next dev` quietly became the
published answer.

Setting `APP_URL` alone would fix today's symptom and leave the trap armed, so:

- [x] **`apps/web/lib/origin.ts`** — one canonical resolver: `APP_URL`, then
      Vercel's own `VERCEL_PROJECT_PRODUCTION_URL` / `VERCEL_URL` (always
      present on Vercel, supplied without a scheme), and localhost **only**
      when nothing indicates a deployment. A deployed build can no longer
      reach the localhost branch even if `APP_URL` is forgotten again.
      Deliberately not derived from the `Host` header: this feeds crawler
      output, and `Host` is attacker-controlled.
- [x] **11 unit tests** pinning each branch, including the exact production
      case (Vercel env present, `APP_URL` absent) and every loopback form.
- [x] **`scripts/check-seo-origin.mjs`** — the CI assertion the audit asked
      for. Next prerenders these routes at build time, so it reads the
      generated bodies directly. **Verified against the real bug**: built
      without an origin it fails and prints the offending body; built with
      Vercel's env it reports `https://apply4you.vercel.app/sitemap.xml`.
- [x] **CI wiring** — the build step now supplies a production-like origin and
      the guard runs after it, so the tested path is the real one.
- [x] **`turbo.json`** — `APP_URL`, `VERCEL_URL` and
      `VERCEL_PROJECT_PRODUCTION_URL` declared as build inputs. Without this
      turbo would replay a cached build whose SEO body names a different host,
      and the guard would be checking a stale artifact.

Still yours: **set `APP_URL` in Vercel Production** to the canonical origin.
The code now degrades to the correct Vercel hostname instead of localhost, but
only `APP_URL` can name a custom domain, and the audit is right that the
`apply4you-web-one` → `apply4you.vercel.app` alias should be settled
deliberately.

### P1-06 (new) · A stale worker build was indistinguishable from a dead one ✅

This is the defect behind the false P0 above, and it will recur on every
deploy that lags the web app.

- [x] The worker now publishes its **commit SHA** in the heartbeat.
- [x] `queueHealth()` reports **`consumerObserved`** — BullMQ marks a job
      `active` only once a worker has claimed it, so an active job is positive
      proof of a consumer, entirely independent of the heartbeat.
- [x] `/api/health/queue` now distinguishes three red states instead of one:

      | state | meaning | action |
      |---|---|---|
      | `unreachable` | Redis did not answer | fix Redis |
      | `no-consumer` | Redis fine, no heartbeat, nothing active | start the worker |
      | `stale-worker-build` | Redis fine, jobs **active**, no heartbeat | redeploy the worker from current master |

      All three remain **503**. An endpoint that goes green on an inference is
      the failure this route exists to prevent; the point is to name the cause,
      not to soften the verdict.
- [x] The watchdog workflow's alert text now explains which state means what.
